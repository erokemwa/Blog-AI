PART ONE

Functions

Before tools, before agents — the humble unit everything is built from. No code background needed.

The most important idea in the building

A function is a defined piece of work

Give it some inputs, it does one well-defined job, it hands back a result. A recipe. A vending machine. A coffee order.

brewCoffee(size, shots, milk) → a cup of coffee. The name says what it does; the parameters shape exactly what comes out.

Live · the parameters decide the outcome

No new function. No new code. Just different parameters → a different result. This is the whole knob the agent gets to turn.

PART TWO

Tools

Plot twist: a tool is just a function — handed to the model, with a label that says what it's for.

Registering a tool

A tool = a function +
a description the model can read

  • Take a function (get_weather).
  • Write a plain-language description & list its parameters.
  • Register it with the agent — it gets appended to the system prompt.
  • Now the model knows the tool exists and how to call it.

What the model actually sees

# appended to the system prompt
tool: get_weather
desc: "current weather for a city"
params: { city: string }

tool: send_email
desc: "send an email to someone"
params: { to, subject, body }

A menu. The model reads the menu and decides what to order.

What an agent is

An agent wraps the model and makes the decisions

The model can't do anything by itself. The agent is the wrapper that:

  • holds the system prompt + tool menu
  • sends context to the model
  • reads back its decision: which tool, which parameters
  • actually runs the tool, then loops

The two kinds of "result" in that trace

Don't confuse these two

Model result

What the model produces: either a tool call (a request — "run this with these parameters") or a final text answer. It's the brain's decision. It never touches the world directly.

Tool result

What the tool hands back after the agent runs it: real data — weather, flights, a created event. This gets fed back into the context as a synthetic prompt, and the loop continues.

The model proposes; the agent executes; the result returns; the model reads it and decides again. That back-and-forth is the loop — which is exactly where we're going.

PART THREE

Loops

A 60-second detour into the most ordinary idea in programming — because the agent is built on it.

The plain idea

Repeat until done

A loop does the same step over and over until some condition is met. Then it stops.

"Keep stirring until the sauce is smooth." The stirring is the loop. "Smooth" is the termination condition.

No exit condition → it runs forever. (Yes, agents can get stuck in loops. We'll come back to that.)

In pseudocode

while ( not done ) {
  do_a_bit_of_work()
  check: are we done?
}
→ exit

Reading the loop you just ran

It runs until the model stops asking

Keeps going while…

the model keeps returning tool calls. Each result enriches the context, so the next decision is better-informed.

Terminates when…

the model returns a plain text answer with no tool call. Nothing left to fetch. Loop exits, user gets the reply.

Safety stops

max iterations, time limits, cost caps — so a confused agent can't loop forever. This is the harness's job. ↘

This exact pattern — input → context → model → tools → repeat → reply — is what every serious agent framework runs, from OpenClaw to Claude Code.

PART FIVE

Feeding
the Loop

Remember synthetic prompts from Lesson 1? Compaction, hooks, and skills are all ways of injecting them.

Three levers on "what the model sees each turn"

Managing the context, automatically

Compaction

The window fills as the loop runs. So the agent summarises old turns into a short note and drops the raw transcript — injected back as a synthetic prompt. Keep going without forgetting the point.

Hooks

Code that fires at set points in the loop — before a tool runs, after a result returns. It can inject extra context, reformat, log, or block an action. Your hands on the wheel mid-loop.

Skills

Packaged instructions + capabilities the agent loads when relevant ("how to write a report"). Pulled into context on demand instead of bloating every prompt.

All three are the same move: quietly shaping the text the model reads on each pass of the loop. The model never knows the difference — that's the point.

PART SIX

The Harness

One more layer out. The thing that makes an agent safe enough to actually let loose.

Wrapping the agent

A harness wraps the agent with guardrails & plumbing

The agent decides what to do. The harness governs how it's allowed to:

  • permissions & sandboxing — what tools it can't touch
  • the loop runner, retries, max-iteration limits
  • guards against prompt injection & runaway cost
  • logging, observability, human-in-the-loop approvals

PART EIGHT

The Lore

We spent the whole lesson giving software agency. The culture has words for agency in people, too.

Vocabulary you'll hear everywhere

Agency — the meme & the mindset

"NPC"

From games — a non-player character running on a fixed script. Used (half-jokingly) for going through the motions on autopilot, waiting to be prompted. Low agency.

"High agency"

The prized trait: seeing what needs doing and just doing it — finding tools, taking initiative, not waiting for permission. The exact behaviour we engineer into agents.

The joke writes itself: we're teaching machines to be high-agency while half of us run like NPCs. The builders who win this era act like the agents they build — point yourself at a goal and loop until it's done.
